# API conventions (V1)

Status: Draft for Approval Gate 4
Sources: TSD v0.1 §7, §8, §9; BRD v0.8 TB-01/TB-02, N4, N5; `docs/domain/*` (Gate 2), `docs/database/*` (Gate 3)
Contracts: `openapi/*.yaml` (OpenAPI 3.1), shared components in `openapi/common.yaml`. Errors: `ERROR_CATALOG.md`.

## 1. Shape

- JSON over HTTPS, versioned under `/v1` (TSD §7). One API serves web and mobile; there is no separate mobile backend.
- **Operations, not table CRUD.** State changes are commands on an aggregate, named after the business action: `POST /v1/leave/requests/{id}/approve`, not `PATCH /leave_requests/{id} {state: approved}`. Plain field edits on mutable master data (branch name, employee contact details) use `PATCH`.
- **Organisation scope is never in the URL or body.** Client routes take the organisation from the verified token (TB-01, TSD §4.1). A body field named `org_id` is rejected. Vendor routes live under `/v1/vendor/...` and use vendor tokens (TSD §4.3).
- Path segments are plural nouns in kebab-case; JSON fields are `snake_case`.
- IDs are UUIDs (v7 generated by the server). Instants are RFC 3339 with offset (stored UTC: BR-11). Business dates are `YYYY-MM-DD`. Times of day are `HH:MM`. Durations are integer **minutes**. Day quantities are decimal strings with 2 places ("0.50").
- **No money fields in V1** (BRX-02).

## 2. Declaration on every operation (build rule, TSD §7)

Every operation in every OpenAPI file carries these extensions. A route without them fails the build:

| Extension | Value | Source |
|---|---|---|
| `x-permission` | One operation code, or a list when the required code depends on the target (e.g. approval level 1 vs 2, or the rule group being edited: PC needs TCP-11, HW needs CMP-01); the description states which applies when from `docs/domain/PERMISSION_MATRIX.md` (e.g. `LVE-03`), or `SELF-AUTH` for sign-in routes, `AUTHENTICATED` for routes any signed-in user may call on their own data (own profile, language, own jobs, upload links), or `SYSTEM` for job endpoints | N5 |
| `x-module` | Module code that must be enabled (`C08`, `M02` …). Always-on common modules still declare theirs. Cross-cutting routes declare their owner: approval inbox `C03`; jobs, upload links and audit `C13` | MD-03, BR-14 |
| `x-scope` | `org` · `branch-department` (AC-07 scope applied) · `team` · `self` · `vendor` | AC-07 |
| `x-audit` | `true` if the operation writes an audit entry (every write does; reads that expose sensitive data too) | §16 |
| `x-events` | Domain events emitted through the outbox (SERVICE_BOUNDARIES §4), or `[]` | ADR-002 |
| `x-idempotent` | `key` (needs an `Idempotency-Key` header), `natural` (repeat is harmless by design), or `n/a` (reads) | TSD §5.5 |

## 3. Authentication

| Who | How | Token carries |
|---|---|---|
| Employee | Mobile number + one-time code (UM-R3) → access token + refresh token | user, organisation, roles, scope |
| Admin users | Email + password + second step where AC-08 is on | same |
| Vendor users | Separate vendor sign-in (OQ-V01-17) | vendor user, vendor role |
| Device gateway | Device serial resolved server-side (TSD §9.1); no user token | device, organisation |
| Jobs | Signed identity token from Cloud Scheduler / Cloud Tasks (TSD §10) | job, organisation |

Access tokens are short-lived, and refresh tokens can be revoked (TSD §8). Sign-in when one mobile number exists in two organisations returns an **organisation choice step** (`409 ORGANISATION_CHOICE_REQUIRED` with the candidate organisation names). Whether that is the final behaviour is OQ-C03-05.

## 4. Checks in order (every request)

1. Token valid → organisation set for the transaction (DATA_MODEL §4).
2. Organisation suspended and operation is a write → `ORG_SUSPENDED` (VC-R4).
3. `x-module` disabled → `MODULE_DISABLED` (MD-03).
4. Role has no grant for `x-permission` → `FORBIDDEN`. Target outside the user's scope → `NOT_FOUND`. A row outside scope is reported as not found, so the API never confirms it exists.
5. Validation → `VALIDATION_FAILED` with field errors.
6. Business rules → specific codes (`PERIOD_LOCKED`, `SELF_APPROVAL_FORBIDDEN`, `ILLEGAL_TRANSITION`, …).

## 5. Retries, concurrency and idempotency

- **Commands** (`POST`) require `Idempotency-Key: <uuid>` when `x-idempotent: key`. The server stores the key with the request fingerprint and response for 24 hours. The same key with the same body returns the stored response, and the same key with a different body returns `IDEMPOTENCY_CONFLICT`.
- **State transitions** are also naturally idempotent (STATE_MACHINES §0): approving an already-approved request returns `200` with the current state and causes no second side effect.
- **Edits to mutable resources** (`PATCH`, and commands that depend on the current version) require `If-Match: <etag>`. A stale ETag returns `PRECONDITION_FAILED`. Every read of such a resource returns an `ETag`.
- **Punches** carry their own `idempotency_key` in the body, because offline batches hold many punches (TSD §9.3).

## 6. Lists and filters

- Cursor pagination: `?limit=50&cursor=...` (max 200). Responses are `{ "items": [...], "next_cursor": "..." | null }`. No total counts on large lists.
- Filters are explicit query parameters per list (e.g. `branch_id`, `from`, `to`, `state`), always applied **after** scope.
- Sorting uses `?sort=field` or `-field`, restricted to listed fields per operation.

## 7. Asynchronous work

- Reports and exports larger than a set size, bulk uploads, bulk recalculation and payroll input exports are **jobs**. `POST` returns `202` with a `Job`, and `GET /v1/jobs/{id}` polls it. A finished job carries a short-lived signed download link (TB-02, TSD §7).
- Uploads use a short-lived signed upload link (`POST /v1/files/upload-links`). The file reference is then passed to the command (TSD §9.2, §11).

## 8. Explanations

Day results and period totals return their **explanation**: ordered steps with rule references and policy version (BR-08). For employees, the API removes the parts that AC-05 visibility settings hide. The calculation itself never runs in the client.

## 9. Language

Users get messages and labels in their language (UM-R4, N7). Problem `title`/`detail` are localised; the `code` is stable and not translated.

## 10. Versioning

Breaking changes go to `/v2`. Additive changes (new optional fields, new operations, new enum values on responses) can ship in `/v1`, and clients must ignore unknown fields. `PayrollInput` has its own contract version (`PayrollInput v1`, DOMAIN_MODEL §7).
