# Data model (V1)

Status: Draft for Approval Gate 3
Sources: `docs/domain/DOMAIN_MODEL.md`, `STATE_MACHINES.md`, `PERMISSION_MATRIX.md` (Gate 2 approved 2026-11-15); TSD v0.1 §4, §5.3, §6, §17; BRD v0.7 TB-01..09
Physical schema: `backend/crates/db/migrations/*.up.sql` (moved there in Phase 5) (PostgreSQL 16, standard features only: TB-06, TSD §17). It is validated on a throwaway local cluster, and no shared or live database was touched.

## 1. Conventions (every migration follows these)

| Topic | Rule | Why |
|---|---|---|
| Schemas | One schema per bounded context: `platform`, `iam`, `org`, `workforce`, `timecap`, `sched`, `policy`, `attendance`, `leave`, `perm`, `period`, `openbal`, `notify`, `audit`, plus `app` (helpers, outbox). | Makes data ownership visible and lets grants follow it (SERVICE_BOUNDARIES §3) |
| Primary keys | Org-owned tables: `PRIMARY KEY (org_id, id)`. Platform tables: `PRIMARY KEY (id)`. `id uuid`, generated by the application as UUIDv7 (time-ordered); `gen_random_uuid()` is only the column default. | Every index starts with the organisation (TSD §4.2); time-ordered IDs keep inserts local |
| Foreign keys | Between org-owned tables, always **composite** `(org_id, x_id) REFERENCES t (org_id, id)`. | The database itself makes a cross-organisation reference impossible (TB-01) |
| Tenant isolation | Every org-owned table is registered with `app.register_tenant_table(...)`, which turns on and **forces** RLS with `org_id = app.current_org()` for reads and writes, and grants the app roles. `app.current_org()` is NULL when not set, so it matches no rows (fails closed: TSD §4.1). | TB-01, AT20 |
| Build check | `app.unprotected_tables` lists every table in a context schema that has no forced RLS and is not in `app.rls_exempt`. CI fails if it returns any row (TSD §4.5). | NFR-01.4 |
| Append-only | Tables registered with `append_only => true` get triggers that reject UPDATE, DELETE and TRUNCATE. | BR-01, §16, BRX-03 |
| Time | Instants: `timestamptz` (stored UTC). Business dates: `date`. Time zones: IANA name `text`, validated against `pg_timezone_names`. Times of day: `time`. Durations: `integer` minutes (or seconds where the BRD uses seconds, PR-02). | BR-11, TSD §5.3 |
| Day quantities | `numeric(5,2)`, multiples of 0.25 (quarter day: DS-06). | Exact; no floating point |
| Money | Not stored in V1 (BRX-02). From V2: amounts `numeric(14,2)` (already rounded per BR-15); rates are never stored at 2 decimals (store the inputs, e.g. salary and divisor, or an unrounded rate); never `float`. | TB-05, BR-15 |
| Enumerations | `text` + `CHECK (x IN (...))`. Values are the state and enumeration names of STATE_MACHINES, in snake_case. | Adding a value is a reviewed migration, not an ALTER TYPE |
| Audit columns | Mutable tables: `created_at`, `created_by`, `updated_at`, `updated_by`. Append-only tables: `created_at`, `created_by` only. | §16 |
| Settings documents | Rule-group settings are `jsonb`, one document per rule group, with `schema_version`. They are validated by the `core` settings schema before saving (TSD §5.4). | Justified exception to "no generic key/value": about 360 settings are data, not columns (TSD §5.4) |
| Soft delete | Not used. List entries are **retired** (`retired_at`), and records with history are ended by dates. | History is preserved |

## 4. Tenancy and access

1. **Each transaction starts with** `SELECT app.set_org($1)`, using the organisation from the verified token. A transaction where this hasn't happened sees no client rows.
2. **Support access** (VC-R6): the API checks for an `active` `platform.support_access_grant`, then sets both `app.org_id` and `app.support_grant_id`. Every `audit.audit_entry` written in that transaction records the grant. Whether writes are allowed is OQ-V01-12; the database does not decide it.
3. **Vendor console** reads `platform.*` only. The organisation-usage figures (VC-R3) come from per-organisation summary rows that a job (J10) writes into `platform`. The console never reads client tables.
4. **Files** (TB-02) are stored only as path, type, size and checksum. The path starts with `org_id`.

## 5. Patterns

### 5.1 Effective dating
- Dated assignments use `valid daterange` with `[)` bounds and an **exclusion constraint** so ranges of the same kind cannot overlap (`EXCLUDE USING gist (org_id WITH =, employee_id WITH =, kind WITH =, valid WITH &&)`), for example a single master branch on each date (EM-R9).
- `shift_version` and `policy_version` use `effective_from` and the SM-POLICYVER `state`. The shared trigger `app.guard_frozen_version()` rejects edits to a version that is `in_force` or `superseded` (G5), and `policy.guard_rule_group()` does the same for its rule groups.
- `leave_type_version`, `permission_type_version` and `organisation_settings_version` are stricter: append-only with no state. The version in force is the latest `effective_from` on or before the date, and a change is always a new row. Consequence for GAP-SM-16: a future-dated version of these cannot be edited, only replaced.

### 5.2 Append-only results and ledgers
- `timecap.raw_punch`, `attendance.day_result`, `day_result_punch`, every `*_ledger_entry`, `*_usage_entry`, `punch_flag_decision`, `app.approval_step` and `audit.audit_entry` are append-only.
- `attendance.attendance_day.current_result_id` points at the current result. Moving the pointer is the only update, and the old result stays readable (BRX-03).
- Ledger idempotency: `UNIQUE (org_id, cause_kind, cause_id, entry_kind)`, so a retried posting is a no-op (LedgerPoster, AT21).

### 5.3 Lock enforcement in the database (BR-06)
`period.lock_coverage (org_id, employee_id, dates daterange, period_id)` is written when a period is locked. Whatever the answer to DP-01, the lock is materialised per employee. A trigger on `attendance.day_result` rejects a new result whose `attendance_date` falls inside a covered range, unless the result is marked `for_adjustment`. Such a result exists only so a `period_adjustment` can reference the corrected calculation, and a second trigger stops it ever becoming the current result. Moving `attendance_day.current_result_id` on a locked date is also refused.

### 5.4 Idempotent ingestion
`timecap.raw_punch UNIQUE (org_id, idempotency_key)`. Device pushes use device serial, device record ID and time. App and web punches use a client-generated key (TSD §9.3).

### 5.5 Outbox (ADR-002)
`app.outbox` is written in the same transaction as the change. The relay (`app_relay`) dispatches rows and sets `dispatched_at`. Consumers are idempotent by `event_id`.

## 6. Indexes

Rule: every index starts with `org_id`. Beyond primary keys, unique keys and FK indexes, the indexes are chosen from the query patterns in the user stories:

| Query | Index |
|---|---|
| Day processing: an employee's punches in a time window (§9.6 step 2) | `raw_punch (org_id, employee_id, event_at)` |
| Unresolved device punches waiting for an enrolment mapping | `raw_punch (org_id, device_id, enrolment_id) WHERE employee_id IS NULL` |
| Daily register, dashboards (R1, R2, DB-R3) | `attendance_day (org_id, attendance_date)` |
| Employee calendar | `attendance_day (org_id, employee_id, attendance_date)` unique |
| Pending approvals for an approver (DB-R5, J3) | `approval_step` and request `(org_id, state, current_approver_id)` partial on pending states |
| Open flags (R5) | `punch_flag (org_id, state) WHERE state = 'raised'` |
| Dispatch | `app.outbox (created_at) WHERE dispatched_at IS NULL` |

Partitioning (TSD §4.6): not in V1. The keys are chosen so `raw_punch`, `day_result` and `audit_entry` can later be partitioned by month without changing their foreign keys. See MIGRATIONS.md §5.

## 7. Decision points and gaps in the schema

| Item | How the schema stays open |
|---|---|
| DP-01 period cycle owner | **Decided D-02: organisation.** V1 uses only `owner_kind = 'organisation'`; `branch` and `policy_set` stay allowed by the CHECK but unused (no migration needed). V2 adds `payroll_group`. |
| DP-03 policy precedence | **Decided D-03:** employee > shift > department > category > branch > organisation; resolver logic, no schema impact. |
| DP-04 schedule time zone | `day_result.schedule_tz` records the zone actually used. |
| DP-05 flag counts before decision | `punch_flag.counts_before_decision` is captured when the flag is raised. |
| DP-06 DS-10 vs LM-28 | No schema impact (rule logic). `attendance_day.processing_state` includes `absence_pending`. |
| DP-07 enrolment ID uniqueness | Exclusion constraint is per **device** (narrowest safe rule). If the answer is per branch or organisation, a stronger constraint is added by migration. |
| DP-08 HR correction second person | `regularisation_request.origin IN ('employee','hr_direct')`; the approval path is not fixed in the schema. |
| DP-09 work from home | No table until decided. |
| DP-10 organisation settings dating | `organisation_settings_version` has `effective_from` (it works for either answer). |
| GAP-SM-08 request draft | No `draft` state in any request CHECK. |
| GAP-SM-16 scheduled policy edit | Trigger blocks edits only for `in_force` and `superseded`; `scheduled` stays editable until decided. |
| G-01..G-40 permissions | Rights are rows in `iam.role_grant`. Default grants are seed data (MIGRATIONS.md §4). "?" cells are seeded as **not granted**. |
